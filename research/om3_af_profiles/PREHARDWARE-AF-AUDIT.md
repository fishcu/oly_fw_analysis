# OM-3 1.1: seven-area offline AF profile audit

1 November 2026. This extends the [66-check baseline](OFFLINE-AF-PROOF.md). Reproduce with `scripts/Run-OM3PrehardwareProof.ps1`; exact sources and outcomes are pinned in `analysis/button-af/prehardware/prehardware-validation.json`.

**The requested per-button mechanism remains technically plausible and executable under emulator fixtures. This audit does not establish a complete camera extension, and the remaining gaps are not all hardware-only.** All seven requested areas were investigated. There are 91 additional passing assertion groups, 18 explicit boundary records and eight before-fix defect reproduction cases. These categories must not be added together and presented as successful feature tests.

The requested behavior is unchanged: each button uses a retained stock target configuration; half-press follows the latest SCP Subject Detect choice, including Off and every supported class; AF-ON bypasses detection; S-AF/C-AF remains shared. AF-ON precedence with both held remains the proposed policy. No detector algorithm or model weights were changed.

## 1. Original shooting-handler continuation

The earlier wrappers stopped at original handler entries. New probes continue through the original bodies at `610b9197`, `610b962a`, `610b9653` and `610b96f0`, with a supplied shooting context and the native profile transition preceding each handler. Strict missing-memory detection stops at the first unavailable runtime read rather than silently interpreting missing RAM as zero.

The minimal continuation stops in the OS allocator at `60024315`, reading `629607a8`, for all four handlers. A second probe supplies explicit bounded heap, kernel-object creation, current-task, non-interrupt-context and uncontended mutex service contracts. It runs the actual property registries `60405865` and `603f215a`, actual lazy constructors and further UI lookup code. Three paths then stop at settings initialization state `a31f4d28` in `60419468`; AF-ON release stops at missing synchronization-object state `62b482d4` in `60ae794e`. These are software runtime initialization dependencies, not evidence of hardware impossibility.

Static continuation identifies the AF-ON policy route through `610a5620` and `610a5a14` to shooting-interface slot `+5c`, implemented by `60b14eb4` (`setAflState` diagnostic). The method constructs request `0x5e9` through `60af491f`, submits via `60b2e356`, and constructs associated request `0x3bf` through `60af64fd`. Four native constructor tests validate the `0x5e9` packet fields for enable/disable and operation kinds 2/4 using supplied allocation buffers. A command constructor is not proof of the later dispatcher or lens command.

**Result:** continuation is materially farther than a wrapper-entry breakpoint, but full shooting-handler → AF transaction → lens submission remains unproved. No UI policy gate was replaced with an unconditional success stub to manufacture completion. Traces: `shooting-continuation-trace-*.txt`, `shooting-runtime-trace-*.txt`.

## 2. Failed and delayed transitions

The old prototype has a reproducible defect: after a failed start/stop wait, another button event submits again while the original command is pending, using the firmware's single deferred replacement slot. Both start- and stop-wait cases reproduce this.

The revised native entry records physical held state, then refuses resubmission while current work or queued commands remain pending after an error. Twelve tests cover six classes × start/stop failure. They deliver the original late completion through the actual callback/FIFO/worker path, then explicitly reconcile the latest held state. No replacement command is submitted by the blocked retry. A native busy guard also rejects nested entry.

**Limit:** this is guarded admission and successful recovery when the harness requests reconciliation. Automatic retry scheduling, rollback of partial UI actions and replay of a rejected original button handler are not wired into the camera dispatcher. A reentrant physical event currently requires caller retry. The result must not be described as complete automatic recovery.

## 3. Stock target options and capture

All 11 recovered stock UI enum values 0–10 pass native four-byte conversion, native ten-byte capture, target activation and bounded search-rectangle checks. Values 6–9 exercise custom dimensions. Each enum is captured and activated for both buttons and all three supplied orientation banks: 66 enum/button/bank combinations.

The ten-byte record retains frame, internal area, size, vertical/horizontal dimensions, priority and C-AF center-start fields. It is generated by stock `609b3c79`, rather than invented from a UI dropdown value. The converter `609b3ecd` and record builder are native; **the bridge that places converted values into internal settings is explicitly supplied by the harness**. The full UI control-to-setting transaction is still missing. The four-byte converter does not encode the separate `MODE_AF_TARGET_SIZE` key `0x9a41`; four additional native tests preserve supplied size values 0/1 for both buttons and verify their native snapshot geometry. These do not establish which camera-facing enum sets each size, so the enum matrix must not be presented as proof of every named stock zone UI behavior.

Stock normalization matters: internal kind 2 forces frame 526; kinds 0/2 clear priority, and kind 3 with vertical dimension 3 also clears it. Preserving stock output avoids treating these transformations as extension bugs. Recovered enum names such as TYPE_1/TYPE_2 are internal labels, not proven camera-facing names for Small/Wide/etc.

**Result:** the stock data representations and their use are tested across recovered enum values. Camera UI capture, exact user-facing label mapping and persistent editing of each button's profile remain unfinished.

## 4. Movement and orientation without changing owner

The old owner/class-only change check missed profile edits. The revised native entry compares the complete selected target record with the active record, so movement or dimension changes trigger native refresh even when owner and subject class are unchanged.

Forty combinations cover five frame positions (0, 38, 526, 1014, 1052), four dimension pairs (1×1, 3×5, 9×13, 27×39) and priority Off/On, with C-AF center-start retained. The stock priority normalization is asserted. Tests check the complete cache and a valid native 640×480 search rectangle. Separate tests change and restore orientation banks, and reject an invalid bank index.

**Limit:** orientation 0/1/2 is a supplied adapter input. Physical orientation-event mapping, movement interception, AF-Home and automatic recapture are not established by writing that input. `609832f5` copies an already-computed override; it is not itself proof of the physical orientation transform.

## 5. Competing commands, re-entry and stale results

The revised controller passes all 224 finite held-state/event edges across seven SCP choices and shared focus modes 0/2. Six competing class-change cases execute the real deferred timer callback `608412c5`, retry body `608413b4`, callback enqueue, native FIFO and worker drain. An actual nested native reconcile during a modeled foreground wait is rejected without changing held bits; the parent finishes and releases its guard.

The outer result publisher `6087215e` is now entered from its real entry. For all six classes, after native stop it takes diagnostic `3106001e` before modifying the seeded 356-byte result buffer. After restart, the same supplied old bytes reach the copy-complete boundary at `608721f6`. There is no generation check before that copy. This does **not** prove stale data is selected downstream or a real camera race: caller provenance, later validation and hardware quiescence matter. The identified direct caller at `608421fa` supplies global buffer `a33a2bf8` from the kind-5 worker path, rather than an arbitrary callback argument.

**Result:** real serialized/deferred machinery and selected re-entry cases work under their contracts. The scheduler model is deterministic and uses independent child stacks; it is not the actual kernel. The busy guard is a byte check/store, not an atomic cross-task lock; serialized dispatcher ownership has not been established. Two adversarial native probes inject a later release immediately before the parent press stores its held state. For each button, the parent then overwrites the release and returns success with the button held. This is a concrete counterexample under that supplied schedule, not proof that the real UI dispatcher permits the schedule. It demonstrates that the byte guard alone is insufficient for arbitrary concurrent input. A serialized event owner or atomic queued admission is required before claiming that broader guarantee. Arbitrary preemption, all producers, interrupt delivery, cross-generation result ownership and automatic rejected-event replay remain unproved.

## 6. Presentation, persistence, custom modes and lifecycle reset

Across all 11 recovered enum values, native consumer `6095be40` reads dimensions from the active cache, and native presentation classifier `60905296` returns the expected classification. Static output builder `60900203` has branches using both the stock accessor and active-cache accessor. The proposed accessor hook affects the former too. These are useful publication inputs, not a complete rendered EVF/SCP/display test.

An additional regression found that a native external stop left the cached owner/class unchanged; the prototype then skipped restarting detection. Six before-fix cases reproduce this. The revised entry checks worker state/class as well as cached configuration; six after-fix cases restore the correct class when reconciliation is called. This tests an external lifecycle reset, **not** actual camera sleep/wake dispatch.

Fresh prototype initialization restores fixture defaults and loses a previously captured frame 100. There is no persistent per-button bank backend, custom-mode serialization, reset policy or camera wake/recall hook. Those are confirmed absent implementation pieces, not successful persistence tests. Seventy-seven related setting-name mappings are inventoried as leads; their presence does not prove a spare safe key exists.

**Result:** selected display inputs and post-reset reconciliation are verified. Persistent profiles, exact custom-mode/sleep/wake behavior, full display publication and settings UI still require software integration.

## 7. Relocation, storage and update packaging

The final native components are controller 548 bytes, reconciliation 739 bytes, capture 165 bytes, mode guard 28 bytes and four 75-byte wrappers: **1,780 packed bytes**. The existing nine-byte accessor replacement remains at its original address and references fixture state. Packed branches/calls are relocated and executed in emulator memory at `60a8f088`; all seven SCP choices pass lifecycle/bypass/restoration and moved-bank capture. Four relocated wrappers preserve all eight general registers and SP before reaching their original handlers.

The examined section-4 FF tail spans `60a8f088`–`60a8f800`, 1,912 bytes, leaving 132 bytes after these components. The test checks every original destination byte is FF. This is a padding observation, **not an allocation or lifetime guarantee**. Emulator writes do not modify the source image. The original sparse fixture still occupies a 4 KiB code mapping, and the compact test retains artificial `0x700c...` data. No camera RAM reservation, loader lifetime, cache-coherence contract or task-stack headroom has been proved. Lowest observed synthetic SP is `7005fe7c`; scheduler child stacks are supplied by the harness.

An in-memory experiment inserts the exact packed code into the actual main component, checks that an unrepaired edit is rejected, then repairs the additive checksum and successfully decodes/re-parses it with original metadata and length preserved. This uses the host component parser. It does not run the native full-component validator, boot authentication, flash writer or recovery chain. No modified component or installable update is saved. Earlier native-validator tests used a small synthetic component and remain limited to that scope.

**Result:** native code size, selected relocation/ABI behavior and host component integrity are workable. Deployment is still conditional on owned data RAM, runtime loading and the complete acceptance/boot/recovery chain.

## Evidence boundary and final assessment

Two prototype defects were reproduced and addressed: duplicate resubmission after failed waits, and skipping detector recovery after an external stop. Same-owner movement handling was added. The final suites retain original settings/images and run Ghidra read-only; temporary mapping changes are discarded. The original baseline suite is rerun separately and remains historical coverage of its original controller, not a substitute for the revised tests.

There is no demonstrated fundamental obstacle to separate target profiles plus AF-ON Subject Detect bypass. There is also no basis yet for saying the complete extension is definitely implementable on-camera or ready to flash. The remaining software work is concrete: full stock configuration/event integration, automatic recovery/replay, actual orientation and lifecycle adapters, persistent profile storage/custom-mode policy, full display publication, result provenance and deployment memory/loading. Physical autofocus quality, lens motion, bursts, latency and device completion additionally require hardware evidence. More offline engineering remains possible; this report does not claim exhaustive closure of every software question.
